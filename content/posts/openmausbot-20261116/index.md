如果你同时用过几款 AI 工具，大概会熟悉这样的工作方式：在一个窗口查资料，在另一个窗口写代码，接着把结果复制给第三个窗口，让它挑挑问题。

单看每一步都挺顺，连起来却有些累。你要反复交代背景，记住谁做到了哪一步，还要把上一位的输出整理成下一位的输入。工具越来越能干，协调工作也越来越多。

OpenMausBot 想把这些动作收进一个熟悉的界面：**一份联系人列表、几个工作频道，以及一群各有分工的 AI 机器人。**

截至 2026 年 11 月 16 日查询时，它在 GitHub 周榜上显示本周新增了 5,463 个 Star。吸引我继续看下去的，是它对个人 AI 工作台的这个设想：当一个人开始同时使用多个 Agent，界面该怎么帮助他把事情组织起来？

## 把 Agent 放进联系人列表

按照[项目 README](https://github.com/milind-soni/OpenMausBot) 的介绍，OpenMausBot 是一个开源、以本地运行为优先的 Agent 应用，也曾使用 MausBot、OpenGrokBot 等名称。

它可以接入本机已安装并登录的 Claude、Codex、Grok CLI，把底层 Agent 的执行过程带进统一的聊天界面。项目还提供自定义引擎接入方式，让使用者按需配置其他模型服务。

在这个界面里，每个机器人都有自己的角色说明、模型选择和工具配置。你可以像管理联系人一样给它起名字、置顶、标记未读，或者复制出一个新的角色。执行任务时，回复和工具活动会持续出现在对话中。

这让一些原本藏在终端和配置文件里的差别，变得容易理解：负责研究的机器人需要资料来源，负责开发的机器人需要工作目录，负责审核的机器人需要明确的检查标准。

**名字帮助你找到它，职责决定它该做什么，模型和工具决定它能做到哪一步。**

## 频道让每件事有自己的上下文

机器人有了分工之后，还需要一个放置工作的地方。

OpenMausBot 提供频道，用来区分工作、个人事务和具体项目。每个频道可以配置独立的对话记录、共享指令、工作目录、参与机器人以及响应规则。

这个设计很适合那些背景长期有效、任务不断变化的工作。比如一个博客频道，可以保留受众、写作风格、内容目录和引用要求；下次换一个选题时，继续在这个工作环境里推进。

从使用者的角度看，可以把配置理解成三件事：

- **机器人**：负责哪一类工作，需要什么能力。
- **频道**：当前项目有哪些背景和约束。
- **任务**：这一轮具体要交付什么，怎样才算完成。

项目还提供自动选择响应机器人的模式，但需要配置相应的路由模型服务。初次使用时，明确指定负责人会更容易观察问题：任务交给了谁、结果由谁整合，都有清楚的落点。

## 用一个博客团队，理解它怎么协作

假设要写一篇介绍开源项目的文章，可以先建立一个“博客编辑部”频道，放入三个机器人：

| 角色 | 主要任务 | 交付物 |
|---|---|---|
| 研究员 | 阅读官方资料、核对功能与限制 | 带来源的事实清单 |
| 作者 | 按博客风格组织文章 | Markdown 初稿 |
| 编辑 | 检查事实、结构和表达 | 修改意见与待核实项 |

这是一种工作流设计示例，具体的任务转交方式仍需要结合频道规则与实际配置。

第一步可以交代研究员：

> 阅读项目的官方 README 和文档，整理定位、核心功能、安装方式与使用限制。每条重要事实附上来源；找不到依据的地方标为待核实。

等事实清单完成，再让作者写初稿，最后交给编辑检查。频道共享指令里则可以提前放好要求：读者是谁、篇幅大致多长、文件放在哪里，以及哪些动作需要先确认。

这套分工能不能节省时间，取决于交接是否清楚。研究员交付了模糊结论，作者就容易把猜测写成事实；编辑没有检查标准，就容易只改措辞。

所以我会先从两个角色开始：一个执行，一个审核。等这条流程稳定了，再判断是否需要单独的研究员、资料管理员或者发布负责人。

多一个机器人，就多一份上下文和协调成本。值得增加的角色，应该对应一个反复出现、能够独立验收的工作环节。

## 给机器人配上电脑和应用

OpenMausBot 的另一部分能力，是让 Agent 接触实际的执行环境。

按项目文档，机器人可以使用云端 Linux 桌面、隔离的本地虚拟机，或在支持的平台与配置下操作当前电脑。界面提供工作画面预览，也有供用户接管桌面的入口。

这给任务增加了实际的落点：读取文件、操作网页、执行命令，以及在获得相应权限后完成跨应用工作。

外部应用连接主要通过 Composio 等集成完成，项目列举了 Gmail、Slack、GitHub、Notion 等服务。接入之后，机器人才有机会把“帮我整理一下”继续推进成读取资料、生成草稿、更新记录等具体动作。

不过，应用出现在连接目录里，只说明有接入路径。账号授权、工具可用性、任务本身的难度，仍会影响最终能否完成。

OpenMausBot 也把权限请求带进了聊天界面。涉及需要授权的命令、文件操作或电脑操作时，用户可以在对话卡片里作出决定。

我比较在意这种交互：**让用户在任务推进到关键动作时，看得见它准备做什么，也有机会接手。** 比起一次性给出很宽的目标，这种节奏更适合逐步建立信任。

## 本地优先，具体指什么

OpenMausBot 会在本机运行管理 Agent 的服务，并把对话记录、事件和配置保存在本地目录。对习惯自己管理文件和工具的人来说，这种部署方式比较容易理解。

同时，完整的数据流仍取决于接入的服务。

使用云端模型时，请求需要发送给模型提供方；使用云电脑、应用连接或托管语音时，也会涉及对应的第三方服务。因此，判断某项任务适不适合交给它，需要看清模型、工具和执行环境各自在哪里运行。

费用也可以拆开来看：

- Agent 使用现有订阅或 API，受各自额度与计费规则约束。
- 云端电脑可能产生独立费用，项目提到的 Boat 在试用后收费。
- 应用连接、语音等扩展能力，可能需要额外账号或密钥。

多机器人并行时，还要算上重复读取上下文、相互交接和复核结果的调用成本。一个人做十分钟就能完成的小任务，未必值得启动一整套团队流程。

许可方面，项目主体采用 Apache-2.0；仓库中的 `enterprise/` 目录有单独许可。计划二次开发或商业使用时，可以继续查看项目的[许可说明](https://github.com/milind-soni/OpenMausBot/blob/main/LICENSING.md)。

## 怎么开始用，比较容易判断价值

对大多数想先体验的人，直接从[发布页](https://github.com/milind-soni/OpenMausBot/releases/latest) 下载桌面应用会更省事。

项目提供 macOS、Windows 和 Ubuntu 24.04 x64 安装包。Linux 版本仍标记为 Beta，各平台的电脑控制与语音能力也有差异，需要按自己的系统查看能力表。

截至本文写作时，README 同时提供了终端启动方式，需要 Node.js 24 或更新版本：

```bash
npx openmausbot
```

首次启动会引导选择 AI 接入方式和模型。桌面安装包已包含管理服务；从源码运行则还需要准备 pnpm 等开发依赖，适合准备修改项目的人。

真正上手后，我建议用一个小任务验证整条流程：

1. 接入一个已经能正常工作的 Agent。
2. 建立一个频道，指定资料目录和输出位置。
3. 让它读取公开资料，生成一份带来源的摘要。
4. 检查工具活动、权限请求和最终文件。
5. 再加入一个审核角色，观察是否减少了人工返工。

这时要看的指标很具体：有没有少复制几次上下文，有没有更容易找到任务状态，输出质量是否稳定，以及出错后能不能迅速定位原因。

这些问题有了答案，再考虑接入更多应用、电脑操作和自动化任务，会更容易判断每项配置是否值得。

## 我最想继续观察的，是交接质量

OpenMausBot 已经把很多个人 Agent 工作台需要的元素放在了一起：角色、频道、模型选择、工具活动、电脑环境和审批卡片。

项目也提供团队配置的导入与分享能力，可以把机器人、频道、指令和工作流程打包复用。这让一套有效的协作方式，有机会变成下一次任务的起点。

但在实际工作中，团队能不能长期有用，还要看几个细节：资料来源能否跟到最终结论，执行失败能否被明确报告，角色之间能否传递完整的交付物，以及用户能否随时知道谁在负责。

目前项目仍处于快速迭代阶段，README 也说明了一些尚在建设的连接能力和平台限制。本文依据项目公开文档整理，具体完成率还需要放进自己的任务里检验。

对我来说，它最值得尝试的场景，是那些已经有固定步骤、会反复发生、又需要人工检查结果的工作。例如资料整理、内容生产、代码修改与复核。

当这样的任务能在一个频道里留下清楚的背景、分工和交付记录，“管理一支 AI 团队”才开始有实际意义。联系人列表提供了入口，真正让人愿意继续用下去的，会是每一次交接都更省心一点。
